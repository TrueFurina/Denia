## 2. 缺陷 A：陈旧锁把「已退出但句柄仍被持有」的 PID 判成活着

### 2.1 现象

`logs/.check_all.lock` 里写着 `{"pid": 12368, "ts": ...}`，`acquire()` 返回
`(False, "已有 check_all 在跑（PID 12368，97s 前启动）")`，而 PID 12368 早已不存在
（`Get-Process -Id 12368` 查不到）。此后每一轮 `check_all` 都停在"已有 check_all 在跑"，
要一直堵到 `STALE_SECONDS`（45 分钟）才自愈。

### 2.2 复现（协议级，不依赖现场）

在仓库里起一个子进程，`terminate()` + `wait()` 之后：

| 探针 | 结果 |
| --- | --- |
| `Popen.poll()` | `1`（确认已退出） |
| `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` | 返回句柄（handle=440） |
| `GetExitCodeProcess` | `0`（不是 `STILL_ACTIVE=259`） |
| 旧 `_pid_alive()` | **True**（误判"还活着"） |

### 2.3 根因

`OpenProcess` 成功只证明**进程对象还在 PID 表里**，不证明进程在跑。进程被强杀后，
只要别处仍握着它的句柄（任务调度器 / 父进程 / 批量任务器 / 调试器），进程对象就
不会从 PID 表消失，于是 `OpenProcess` 一直成功、`GetExitCodeProcess` 返回真实退出码
（0），旧实现却只看前者。

### 2.4 已排除的假设

| 假设 | 结论 | 证据 |
| --- | --- | --- |
| 真的还有 check_all 在跑 | 排除 | `Get-Process -Id 12368` 无此进程；子进程探针同样 `poll()=1` |
| PID 被系统复用给了别的活进程 | 排除 | 探针里 PID 指向的就是自己刚 `wait()` 掉的子进程；锁里 `ts` 只有 97s，远小于 45 分钟 |
| 锁文件写坏（半截 JSON）导致误判 | 排除 | 锁文件 JSON 完整，`pid`/`ts` 都在；坏 JSON 那条路径另有判据（第 4 节） |
| 只在"非正常退出"才出现，正常退出无影响 | 成立但不影响结论 | 这正是 `release()` 不执行的情形（强杀 / 崩溃 / 任务被杀），本来就是陈旧锁要覆盖的场景 |

### 2.5 改动

`tools/_gate_lock.py`

- `_pid_alive()` 改为**以退出码为准**：`STILL_ACTIVE(259)` 才是在跑。
- 新增常量 `STILL_ACTIVE = 259`。
- 按 `AGENTS.md` 第三条硬约束补 `argtypes/restype`：`OpenProcess` / `CloseHandle` 的
  HANDLE 取 `c_void_p`（否则 32 位截断），`GetExitCodeProcess` 的 `POINTER(c_uint32)`。
- `GetExitCodeProcess` 失败（权限不足等）时**保守判"活着"**，仍交给时间阈值裁决 ——
  不因为问不到就把别人的锁删掉。

### 2.6 验证

| 命令 | 结果 |
| --- | --- |
| `tools/test_gate_lock.py` | **16 PASS / 0 FAIL**（新增第 5 节 4 条） |
| `tools/_qc_gate_lock_mutation.py` | **五刀全红 + 还原字节一致 True** |
| `python -m compileall -q src tools main.py` | exit 0 |

新增的 4 条回归（第 5 节）：

1. 子进程已退出（`poll()` 非 None）；
2. `Popen._handle` 非 None —— **复现条件成立**（句柄还被持有）；
3. 已退出的 PID 判为已死；
4. 拿这个 PID 写锁，`acquire()` 必须能拿到。

变异第五刀 E（`return code.value == STILL_ACTIVE` → `return True`）被抓住的报错正是
`FAIL 僵尸 PID 的锁不阻塞新一轮 ← 已有 check_all 在跑` —— 说明这道判据真的在守这件事。

## 3. 缺陷 B：`test_wake_word.py` 在干净 venv 里必现假红（用例缺件，不是产品缺陷）

只装 `requirements-test.txt` 的 venv 里跑 `tools/check_all.py`，"唤醒词命中"闸门红：

| 假设 | 结论 | 证据 |

- `src/tests/test_wake_word.py`

## 7. 缺陷 C：`test_doctor.py` 的失败计数被局部变量遮蔽 —— 门禁假绿

### 7.1 现象

为了验第 8 节的 UCRT 判据，我把 `doctor._ucrt_loadable` 临时改成"永远返回 True"
（刀 B）。按设计这会让 9.5a / 9.5b 两条断言失败。实际：

```
  ✗ 缺 UCRT 必须 FAIL（实得 PASS）
  ✗ 只缺 api-ms-win-crt-runtime 也要 FAIL（实得 PASS：…）
  …
PASS：doctor 自检结构成立
exit=0
```

**打印了 ✗，进程却 exit 0，最后还打 `PASS`。** 这正是仓库最忌讳的"假绿"：
门禁看着绿，判据其实已经坏了。

### 7.2 根因

`test_doctor.py` 的 `main()` 里（第 88 行，原样）：

```python
_fails = [r for r in rows if r[0] == doctor.FAIL]
check(not _fails, "当前开发机不应有 FAIL" ...)
```

模块级第 22 行有 `_fails: list[str] = []`，而 `check()` 往里 append。但 `main()` 里
**任何一处给 `_fails` 赋值**，Python 的作用域规则就让它在整个 `main()` 内变成**局部变量**。
于是：

- `check()` 追加的仍然是**模块级**那份 → 断言失败确实被记下了；
- 结尾 `if _fails:`（第 668 行）读的却是**局部**那份 = "doctor 跑出来的 FAIL 行"。

两者不是同一个对象。结果：**只要 doctor 自身在开发机上没有 FAIL 行，其它任何断言失败都不影响退出码**。
第一轮那次"1 项未通过、exit 1"很可能是巧合——恰好 doctor 真报了一条 UCRT FAIL 行，
让局部 `_fails` 非空，才把退出码顶成 1（这一条是**推断**，没有单独做对照实验）。

### 7.3 已排除的假设

| # | 假设 | 结论 | 怎么判的 / 结果 |
| --- | --- | --- | --- |
| 1 | `check()` 没把失败记下来（记数逻辑坏了） | 排除 | 同一份 `_fails` 在别处能生效：把 9 节之外的断言故意弄红，`_fails` 长度会变；日志里 ✗ 行确实是 `check()` 打的 |
| 2 | 刀 B 没生效（改错了地方） | 排除 | 刀 B 后 9.5a 的 detail 变成 `系统 Universal CRT 可加载（API Set 转发正常…）`，即 PASS 分支真的被执行了；diff 字节数为 68891 vs 68957 |
| 3 | 是"退出码没接上"（脚本结尾没 `sys.exit(main())`） | 排除 | 文件末尾就是 `raise SystemExit(main())`（第 680 行）；而且刀 A 能正常 exit 1 —— 出口通路没问题 |
| 4 | 只是这一条断言写得不对 | 排除 | 刀 B 触发的是 2 条 ✗（改完计数器后同一把刀是 **4 条 ✗**），其它节的断言同样不计入 → 是**计数通道**坏了，不是某条断言 |

### 7.4 改动（1 行级）

`src/tests/test_doctor.py`：把 `main()` 内的局部变量改名 `fail_rows`（3 处引用），
并加注释说明"这里不能叫 `_fails`，否则整个 main() 的 `_fails` 都成了局部变量"。

### 7.5 验证

| 场景 | 改之前 | 改之后 |
| --- | --- | --- |
| 落地状态（无变异） | exit 0 / `PASS` | **exit 0 / `PASS`，0 条 ✗** |
| 刀 A：UCRT 判据退回 `os.path.isfile` | exit 1（但只报 1 项） | **exit 1 / `FAIL：2 项未通过`** |
| 刀 B：加载探测恒真 | **exit 0 / `PASS`（假绿）** | **exit 1 / `FAIL：4 项未通过`** |
| 刀 C：加载探测恒假 | exit 1 | **exit 1 / `FAIL：2 项未通过`** |
| 三把刀跑完还原 doctor.py | — | **字节一致 True** |

同一类坑的全仓扫描（AST，692 个 `.py`，`src/` + `tools/`）：

## 8. 缺陷 D：doctor 的 UCRT 判据退化——用"文件在不在"判 API Set 名字

### 8.1 现象

补装依赖后 `test_doctor.py` 只剩 1 项红：

```
✗ 当前开发机不应有 FAIL（否则说明 doctor 自检查出真问题）；
  实际 FAIL: UCRT：缺：api-ms-win-crt-runtime-l1-1-0.dll —— numpy/scipy 等扩展会 DLL load failed
```

但这台机器上 **numpy 明明跑得好好的**（同一 venv 里 `numpy 2.5.4`、vosk、KaldiRecognizer 全都在用）。

### 8.2 取证

| 探针 | 结果 |
| --- | --- |
| OS | Windows 10 专业版 **10.0.19045** |
| `System32\api-ms-win-crt-*.dll` 物理文件数 | **0** |
| `System32\ucrtbase.dll` | 存在 |
| `ctypes.WinDLL("api-ms-win-crt-runtime-l1-1-0.dll")` | **LOAD OK，handle=140732341026816** |
| `ctypes.WinDLL("ucrtbase.dll")` | LOAD OK，**同一个 handle**（=140732341026816） |
| `ucrtbase._getcwd` 绑定 | OK |
| `import numpy` | **2.5.4 OK** |

也就是说：这些 `api-ms-win-crt-*` 名字在 Win10+ 上是 **API Set 逻辑名**，
由加载器转发到 `ucrtbase.dll`，**不需要实体文件**。doctor 用
`os.path.isfile(System32\<name>)` 判存在性，在这类健康机器上必然误报 FAIL。

### 8.3 为什么说是"退化"，不是"设计如此"

本机装的是**已发布的 0.2.0 包**（`C:\Users\Administrator\AppData\Local\DaniaAI`），
它的 `tools/doctor.py` 里这一项**已经是试加载实现**，跑出来是：

```
[PASS] UCRT   系统 Universal CRT 可加载（API Set 转发正常，numpy 等扩展依赖它）
汇总：16 PASS / 3 WARN / 0 FAIL
```

即**仓库 master 上的 doctor 比已发布包旧**。所以这不是"要不要改设计"的争论，
而是把已经验证过的修法补回仓库。

### 8.4 已排除的假设

| # | 假设 | 结论 | 怎么判的 / 结果 |
| --- | --- | --- | --- |
| 1 | 这台机器的 UCRT 真的被裁剪了（doctor 没误报） | 排除 | `LoadLibrary` 两个名字都成功、handle 相同；`ucrtbase._getcwd` 可绑定；`numpy 2.5.4` import OK —— 依赖 UCRT 的扩展端到端可用 |
| 2 | 只是"文件不在 System32，在 SysWOW64 / WinSxS / app-local" | 排除（对判据而言） | `SysWOW64` 也没有；即便在别处，`isfile(System32)` 这个判据仍然会误报，问题在判据不在文件位置 |
| 3 | 是测试环境（venv 3.13）特有 | 排除 | 同一台机器上**安装版**（内置 3.12.10、isolated 模式）的 doctor 输出 UCRT PASS |
| 4 | master 的写法是有意为之（比如要兼容 Win7） | 部分成立，但结论不变 | Win7/8 缺 KB2999226 时试加载会**真的失败** → 仍报 FAIL 并给补丁号；试加载同时覆盖新旧系统 |

### 8.5 改动

`tools/doctor.py`

- 新增 `_win_dll(name)`：加载器入口，抽成函数是为了**能被测试注入**。
- 新增 `_ucrt_loadable(name)`：`try: _win_dll(name) → True / except OSError → False`。
- `check_ucrt()` 改成**试加载** `("api-ms-win-crt-runtime-l1-1-0.dll", "ucrtbase.dll")`，
  PASS/FAIL 文案与已发布包 0.2.0 对齐（"系统 Universal CRT 可加载（API Set 转发正常…）" /
  "无法加载：… —— numpy 等扩展会 DLL load failed"，提示保留 KB2999226 与 `sfc /scannow`）。

### 8.6 验证

| 命令 | 结果 |
| --- | --- |
| `src/tests/test_doctor.py`（落地状态） | **exit 0 / PASS，0 条 ✗**（原先那条 UCRT FAIL 消失） |
| 刀 A（退回 `os.path.isfile`） | exit 1，`FAIL：2 项未通过` |
| 刀 B（探测恒真） | exit 1，`FAIL：4 项未通过` |
| 刀 C（探测恒假） | exit 1，`FAIL：2 项未通过` |

新增/改写的 3 条断言（第 9.5 节）：

- **9.5a** 两个名字都加载不了（= Win7 没装 KB2999226 的形态）→ FAIL，点名 `ucrtbase.dll`，提示给补丁号；
- **9.5b** 只有 `api-ms-win-crt-runtime-l1-1-0.dll` 加载不了 → FAIL，且点名它；
- **9.5c** 真机形态：System32 里**没有**那两个实体文件，但加载器能解析 → 必须 PASS。
  这条就是本机被误判的那一次，专门用来锁住"文件不在 ≠ 用不了"。

> 注入点选在 `_win_dll`（加载器）而不是 `_ucrt_loadable`（判据）：
> 第一版把判据整个替换掉，刀 B 改成"恒真"后测试仍绿——**刀砍在影子上**。
> 换成注入加载器后，判据的真实实现才被覆盖到（刀 B 立刻转红）。

## 9. 诚实边界（第二轮）

- 第 6 节那 7 个闸门是"装了可选依赖"才绿的，`ci.yml` 不装这些包 → **CI 上它们仍然不跑**，
  等于这批行为（托盘、抓屏低频、真合成、在场感、ASR 语音链路）在 CI 里没有守门人。这是
  仓库层面的覆盖缺口，本 PR 只记录、不改 CI（改 CI 要动 workflow 与耗时预算，超出本次范围）。
- 第 7 节的假绿只在这一个文件里被证实；全仓 AST 扫过（692 文件）确实只剩这一处，
  但**动态遮蔽**（`globals()` / `eval` / 局部函数注入）这类写法 AST 扫不到，没做。
- 第 8 节的修法与已发布包 0.2.0 对齐，但**没有**在 Win7/8（无 KB2999226）真机上验过
  "试加载会失败"，只验了"加载失败 → FAIL"这条分支（用注入）。
- 仍未验：`imagehash` 那条（感知哈希）——项目刻意不装，属已知豁免；ffmpeg / Node 相关门禁
  本机没有工具链，没跑。
