| 配置项 | **0 个** | **0 个** |

**关键发现**：后端 `get_memory_settings` / `save_memory_settings` **早已支持 6 项配置**
（`enabled` / `mode`(jarvis|legacy) / `semantic_search` / `intent_judge` / `inject_context` / `max_items`），
`Backend.getMemory()` / `saveMemory()` 也早已导出 —— 但**两个入口都没有把它们做成 UI**。
也就是说：记忆库真正缺的不是"内容浏览"，是"**配置**"。

## 十、方案对比与建议

### 方案 A —— 并存：设置管配置、独立页管内容 ✅ **采用**
- 设置「记忆库」= **配置**（6 项）+ 真实统计摘要（条数 + 三分类）+ 「打开记忆库」入口
- 独立页 = **内容浏览**（列表/命中次数/时间）+ 清空
- 理由：
  1. **职责分离**：设置页是"改行为"，数据页是"看数据"。把 80 条列表塞进设置，会让设置页变成第二个数据页。
  2. **后端本来就是这么切的**：`get_memory_settings` 一次同时返回 `config + stats`，而 `items` 列表是给内容页的 —— 接口边界已经暗示了分工。
  3. **成本最低**：只需把已有 API 接上 + 换成真值统计 + 加一个入口，不动信息架构，回归风险小。

### 方案 B —— 整体迁移进设置并升级 ❌ **不推荐（除非另行立项）**
- 表面优点：单一入口，不用两处找。
- 实际代价：设置页是 5300 行单文件，再塞"列表 / 筛选 / 分页 / 单条详情"会继续膨胀；
  "设置"与"数据管理"混层，用户更难找；侧栏「记忆库」这一项会消失，使用习惯被推翻。
  这已经不是"设置整理"，而是"记忆管理"大改版。
- **若将来真要做，方向应该反过来**：把**配置**也收进独立「记忆库」页做 tab（设置瘦身），
  而不是把数据搬进设置页。

### 两方案都适用的升级项（后端待补）
独立页目前**只能看和全清**，缺：按类型筛选、条目搜索、**删除单条**、手动添加记忆。
后端现有 API 只有 `clear_memory`，需要新增 `delete_memory` / `search_memory` —— 列为后续项。

## 十二、搜索重写（核心）

**旧实现**：`groups.push({hay: group.textContent.toLowerCase()})` → `hay.indexOf(q) >= 0`。
→ 命中粒度是整个 group、且**任何出现在说明文字里的通用词都会命中**；结果不排序；命中了也指不到具体哪一条。

**新实现（四层）**：
1. **拆索引**：把每个 group 拆成 `title`（组标题）/ `labels`（各控件标签）/ `hints`（提示与说明）三段分别存。
2. **加权打分**：标题 100 / 控件标签 80 / 正文 12；同义词按 0.85 折算。
3. **丢弃噪音**：**低于 20 分（即只在正文里出现）默认丢弃** —— 这就是"结果不准"的主因；
   只有在没有任何强命中时才回落到正文命中。
4. **同义扩展 + 推荐**：`SYN` 同义簇（28 组）做双向查询扩展；
   有结果时给"相关词"（同簇其余说法），零结果时给"猜你想找"；点 chip 直接换词重搜。

**按相关度排序**（原来完全不排序），并对命中的**具体控件行**加 `.set-hit-row` 高亮。
