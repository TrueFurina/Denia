## 一、模型挂载异常 / 三角洲提示词误注入

### 现象
未打开《三角洲行动》，但状态卡显示：
`专属提示词（三角洲行动陪伴）已写入会话，模型载入中…`，且一直停在"载入中"，本地双工无任何输出。

### 定位过程（代码链路）
1. 这句话的唯一来源：`src/llm/local_omni_duplex.py:1563`
   ```python
   {"type": "prepared", "msg": f"专属提示词（{self._instruction_label}）已写入会话，模型载入中…"}
   ```
   → 说明是**本地 Comni 全双工**会话（`wss://localhost:8006/...`）。
2. `_instruction_label` 由 `proactive.py:_resolve_duplex_instruction_label()` 解析：
   当 `_duplex_injected_kb_id` 以 `game:` 开头且 `game_knowledge._current.id` 匹配时
   → 返回 `f"{name}陪伴"`，即"**三角洲行动陪伴**"。
   → 反推：**游戏识别确实把当前判定成了三角洲**（`game:delta_force`）。
3. 识别入口：`proactive._duplex_refresh_loop()` 每 10s 调
   `game_knowledge.detect(前台窗口标题, 前台进程名)`；命中规则（`game_knowledge.py:586`）：
   ```python
   _by_title = any(kw in 标题 for kw in keywords)   # 标题含 "三角洲" / "delta force" / "deltaforce"
   _by_exe   = 进程名 in exe列表
   ```
4. **发现的硬伤**：`config.yaml` 里 `games[delta_force].exe` 含
   ```
   DeltaForceClient.exe / DeltaForce.exe / Client-Win64-Shipping.exe / df_helper_main.exe
   ```
   `Client-Win64-Shipping.exe` 是 **Unreal Engine 通用 shipping 进程名**，几乎所有 UE 打包程序都叫这个。
   而 `data/heavy_apps.learned.json` 里也确实躺着 `client-win64-shipping.exe`、`unity.exe`。
   → **只要前台是"某个 UE 程序"，就会被判定成在玩三角洲**，与用户是否打开三角洲无关。

### 结论
- **开启混合档后开始挂载本地模型 = 预期行为**：混合档 = 本地 + 云端，启用即会准备本地 Comni 引擎。
- **自动注入"三角洲"提示词 = 非预期**，是**游戏识别的假阳性**：exe 白名单含通用进程名 + 标题子串匹配，
  没有置信度、没有去抖、没有第二证据（OCR / 是否真在全屏游戏）复核。
- **一直"挂载中" + 双工无输出 = 本地引擎没真正就绪**：
  UI 上那句"模型载入中…"是客户端**自己**在发完 `prepare` 后立刻打的状态（阶段①）；
  真正的"就绪"要等 Comni 服务端回 `{"type":"prepared"}`（阶段②，`local_omni_duplex.py:2443`）。
  一直不升级 ⇒ 阶段②从未到达 ⇒ 本地模型没加载成功 / Comni 没在跑（`config.yaml` 里
  `local_omni_engine.auto_start: false`，需要外部已启动 Comni）。
  另有已知引擎故障会明确卡在这里：Comni 的 `cpp_backend_XXXXXX` 临时目录被清理（清理 C 盘导致）。

### 是否可优化 / 修复
**可以，且分成两层：**

| 层 | 建议 | 风险 |
|---|---|---|
| 识别层（治误判） | ① 删掉 `Client-Win64-Shipping.exe` 这类**通用** exe，或改成"exe + 路径特征串"双重命中；② 标题命中要求"游戏名 + 至少一条第二证据"；③ 连续 N 次命中才认（去抖），并设最短停留 | 低（配置 + `detect()` 判据） |
| 反馈层（治不可观测） | ④ 界面显式写出"识别为：三角洲行动"并给**一键纠正**（"我没在玩这个"），把误判变成可反馈信号 | 低 |
| 引擎层（治卡死） | ⑤ 阶段①/② 用**不同 type 或字段**区分，别都叫 `prepared`（现在 UI 无法分辨"会话已建"与"模型就绪"）；⑥ 给阶段②加**超时**并明确提示（"本地模型 120s 未就绪：检查 Comni 是否已启动 / 临时目录是否被清理"）；⑦ 混合档首次启用时若本地引擎未启动，先给引导而不是静默等 | 中（涉及通话/双工主链路，建议单独一轮改动 + 真机回归） |

> ⚠️ 本轮**没有**动识别配置与通话链路：它们属于"本体功能"（桌宠互动/通话），
> 改动面大且必须真机验证。上面 5 条我按"识别层 → 反馈层 → 引擎层"排了优先级，你点头我就按顺序做。

## 二、设置页跳转卡顿（记忆库 / 开发者页）

### 现象
从设置页跳到记忆库、开发者页，每次约 1 秒多卡顿。

### 定位过程（真机测量，先排除"加载慢"）
用无头 Edge + 模拟 App 静态服务（复刻 `/_spa/<ts>/<file>` + `?v=` 启动令牌）实测：

| 动作 | 新页 DOM 出现 | 长任务(≥40ms) |
|---|---|---|
| 设置页（冷） | 90 ms | 51 / 299 ms |
| 开发者页（冷） | 89 ms | 58 ms |
| 记忆库（热） | 24 ms | — |

**DOM 出现其实很快（<100ms）**，SPA 机制本身不慢。于是改测"内容什么时候**真正可见**"：

```
VIS memory:    tDom=47ms   tVis=642ms    ← 642ms 才完全不透明
VIS developer: tDom=94ms   tVis=641ms
```

### 根因（两处叠加，都是"入场动画"）
1. **每个子页结尾都有一段"逐卡淡入"** —— 记忆库、开发者、角色、日报、主对话页都有：
   ```js
   if (window.gsap && !reduce){
     gsap.from('.top',            {opacity:0, y:-6, duration:.4});
     gsap.from('.kicker, .lead',  {opacity:0, y:8,  duration:.45, delay:.18});
     gsap.from('.mem-stats, .card',{opacity:0, y:16, duration:.5, stagger:.08, delay:.28}); // dev 用 '.card'
   }
   ```
   卡片数量多时，最后一张要到 `0.28 + n×0.08 + 0.5` ≈ **1s 以上**才到位 —— 正好对上"卡顿 1 秒多"的观感。
2. `ui_shared.css` 里 `.app > .main{ animation: pageEnter .42s var(--ease) both; }`，
   `@keyframes pageEnter{ from{opacity:0; transform:translateY(10px)} }` —— 只要 `.main` 是新插入节点就重播，
   SPA 切页每次都播，又叠加 0.42s 的"从全透明起步"。
   ⚠️ 顺带一个**隐藏风险**：本项目已踩过"部分 WebView 不跑 keyframes"的坑，
   `animation ... both` 一旦不跑就会**永久停在 `from`（透明）态 → 整页看不见**。

### 结论
**不是加载慢，是"内容先不可见、再慢慢浮现"**。因为它是**动画重播**，所以"优化加载"没有意义；
真正要做的是"**切页不重播入场动画**"。也**不需要**改成转圈加载 —— 实测切页本身只有 24–94ms，
加转圈反而会闪一下。

### 已实施（本轮已修，实测生效）
| 改动 | 文件 | 说明 |
|---|---|---|
| 切页置 `window.__SPA_NAV`（1.2s 后自动复位） | `spa.js` | 入场动画只属于"首次进入该页"的仪式感 |
| 6 个子页入场守卫加 `&& !window.__SPA_NAV` | `ui_redesign_{memory,developer,characters,daily,main,settings}.html` | 切页跳过逐卡淡入；首屏仍保留 |
| `pageEnter` 去掉 `opacity:0`，并去掉 `both` | `ui_shared.css` | 内容**始终可见**；即使动画不跑也是自然终态（消除永久透明风险） |

**复测（同一套真机脚本）：**

| | 修改前 | 修改后 |
|---|---|---|
| 记忆库 内容可见 | 642 ms | **38 ms** |
| 开发者 内容可见 | 641 ms | **93 ms** |
| 切页长任务 | 51–299 ms | 基本无 |

> 设置页/主对话页原本就是"只做位移、不用 opacity:0"的安全写法（代码里有注释说明原因），
> 本次是把记忆库/开发者/角色/日报**对齐到同一约定**。

## 三、记忆库方案来源（自研 vs Jarvis）

### 核查结果
`src/companion/memory_store.py` 文件头写得很清楚（也对照了实现）：

```python
两种方案（mode 可切换，UI 开关对比）：
- legacy：原版扁平记忆，按最近更新召回（对比用）
- jarvis：借鉴开源项目 isair/jarvis 的 purpose-driven 记忆——
  1. 记忆分类 directive(指令,逐字) / user(偏好) / world(外部事实)
  2. 指令特权注入（用户明确要求永远在最前）
  3. 重要性加权（access hits）
  4. 语义检索（nomic-embed-text 本地嵌入）
```

实现侧全部是本仓库自己的代码：`MemoryStore` 类、`MEMORY_EXTRACT_PROMPT` / `MEMORY_FACTS_PROMPT`、
180 天 TTL 冷归档、来源白名单（chat/duplex/operation/user）、进程级单例、`memory_assembler.py` 注入编排。

### 结论
- **是自研的一整套提取与注入逻辑**，不是"跑着别人的 Jarvis"。
- `jarvis` 只是**方案代号**，来源是"当初借鉴开源项目 `isair/jarvis` 的 purpose-driven 思路"。
- **文案确实有问题**：设置页把代号当产品名露出（`Jarvis` / `Legacy` 按钮），
  记忆库页更是直接把后端原始值打出来（`modeEl.textContent = (r.mode||'jarvis')` → 界面上显示英文 `jarvis`）。

### 已实施（本轮已修）
| 位置 | 改前 | 改后 |
|---|---|---|
| 设置 → 数据与隐私 → 记忆方案（按钮） | `Jarvis` / `Legacy` | **`分类记忆` / `整段摘要`** |
| 同处说明文字 | `Jarvis=分类存储+检索召回；Legacy=旧版整段摘要` | 说明 + **新增一段 note 明确"两种方案都是本软件自研"** |
| 切换提示 toast | `记忆方案已切到 jarvis` | `记忆方案已切到 分类记忆` |
| 记忆库页 方案展示 | 显示原始 `jarvis` | `分类记忆`（新增 `modeLabel()` 映射） |

> 后端 `mode` 取值**仍是** `jarvis` / `legacy`（`webapp.py:13976` 校验、`memory_store.py:397` 判定），
> 只改**展示层**，不动接口 —— 零回归风险。

## 四、搜索纯数字也能命中

### 现象
设置页搜索输入 `1.2.3` 这类纯数字，能匹配到设置项。

### 定位过程（真机复现，改前）
```
"1"     → 命中 2 项   （双工、显存预算）
"1."    → 命中 1 项   （双工）
"16"    → 命中 1 项   （双工）
"0.5"   → 命中 1 项   （双工）
```
命中的都是**正文说明里的数值参数**，例如：
- 通话与双工：`开=1 个锚点即可说；关=至少 2 个一致锚点`
- 通话与双工：`16~24 兼顾清晰与速度（本地双工）`
- 通话与双工：`云端开销：…约 0.5fps…`

### 根因
搜索索引把每个设置组拆成 `标题(100分) / 控件标签(80分) / 正文提示(12分)` 三段加权，
但 `run()` 里有这一句：
```js
var hit = strong.length ? strong : prose;   // 没有强命中时回落到"正文命中"
```
**正文命中（12 分）在没有任何强命中时会被提升为结果**。而正文里塞满了数值参数，
于是任何数字都能靠"说明文字里的数字"命中设置组 —— 这就是"搜索逻辑薄弱"的根。

### 结论
不是"数字被特殊处理"，而是**匹配目标从"设置项名称"漂移到了"说明文字"**。

### 已实施（本轮已修，实测 0 命中）
| 改动 | 说明 |
|---|---|
| 新增**查询质量闸门** `wordless = !/\p{L}/u.test(q)` | 纯数字/符号（无任何字母或汉字）→ 不做同义扩展、**不看正文**、**不回落正文命中** |
| `scoreOf(it, terms, allowProse)` | `allowProse=false` 时完全不查 `.hint/.note` |
| `expand(q)` 早退 | 纯数字查询不做同义扩展（同义表全是中英文词，对它匹配只产生噪声） |
| 零结果文案 | 纯数字查询给专门解释 + 「试试：语音 / 双工 / 看屏 / 模型 / 记忆 / 主题 / 电脑控制 / 社交渠道」 |

**复测（改后）：** `1` / `1.` / `1.2` / `1.2.3` / `16` / `0.5` / `9001` → **全部 0 命中**，
并提示"搜索按**设置项名称**匹配，数字/符号没有对应的设置项（设置项名里不含数字）"。
中英文查询不受影响（`音色` 仍命中 4 项并给相关词推荐）。

### 还可继续优化（未做）
- **分词化匹配**：目前仍是 `indexOf` 子串匹配（中文可接受，英文/数字建议按"整词边界"匹配），
  可进一步避免 `key` 命中 `按键` 之外的长串。
- **拼音/首字母**：`yinse` → 音色。
- 把搜索索引从"每次输入重建"改成"页面就绪时建一次 + DOM 变更时失效"（目前每次 `run()` 都遍历全 DOM，
  5721 行的设置页在低端机可能有轻微输入延迟）。
