# 2026-11-08 外部测试记录：门禁锁的僵尸 PID + 唤醒词用例的两处缺件

> 在**干净的 Windows 机器**（无 git、无 Node、无 ffmpeg，只有系统 Python + 一个只装
> `requirements-test.txt` 的 venv）上，把 `ci.yml` 的三条腿与 `tools/check_all.py`
> 全量门禁各跑了一遍。结论：**2 处真问题，都落在"门禁本身"上**，产品代码没动。

## 1. 口径与环境

| 项 | 值 |

## 2. 缺陷 A：陈旧锁把「已退出但句柄仍被持有」的 PID 判成活着

### 2.1 现象

`logs/.check_all.lock` 里写着 `{"pid": 12368, "ts": ...}`，`acquire()` 返回
`(False, "已有 check_all 在跑（PID 12368，97s 前启动）")`，而 PID 12368 早已不存在
（`Get-Process -Id 12368` 查不到）。此后每一轮 `check_all` 都停在"已有 check_all 在跑"，
要一直堵到 `STALE_SECONDS`（45 分钟）才自愈。

### 2.2 复现（协议级，不依赖现场）

在仓库里起一个子进程，`terminate()` + `wait()` 之后：

| 探针 | 结果 |
| --- | --- |
| `Popen.poll()` | `1`（确认已退出） |
| `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` | 返回句柄（handle=440） |
| `GetExitCodeProcess` | `0`（不是 `STILL_ACTIVE=259`） |
| 旧 `_pid_alive()` | **True**（误判"还活着"） |

### 2.3 根因

`OpenProcess` 成功只证明**进程对象还在 PID 表里**，不证明进程在跑。进程被强杀后，
只要别处仍握着它的句柄（任务调度器 / 父进程 / 批量任务器 / 调试器），进程对象就
不会从 PID 表消失，于是 `OpenProcess` 一直成功、`GetExitCodeProcess` 返回真实退出码
（0），旧实现却只看前者。

### 2.4 已排除的假设

| 假设 | 结论 | 证据 |
| --- | --- | --- |
| 真的还有 check_all 在跑 | 排除 | `Get-Process -Id 12368` 无此进程；子进程探针同样 `poll()=1` |
| PID 被系统复用给了别的活进程 | 排除 | 探针里 PID 指向的就是自己刚 `wait()` 掉的子进程；锁里 `ts` 只有 97s，远小于 45 分钟 |
| 锁文件写坏（半截 JSON）导致误判 | 排除 | 锁文件 JSON 完整，`pid`/`ts` 都在；坏 JSON 那条路径另有判据（第 4 节） |
| 只在"非正常退出"才出现，正常退出无影响 | 成立但不影响结论 | 这正是 `release()` 不执行的情形（强杀 / 崩溃 / 任务被杀），本来就是陈旧锁要覆盖的场景 |

### 2.5 改动

`tools/_gate_lock.py`

- `_pid_alive()` 改为**以退出码为准**：`STILL_ACTIVE(259)` 才是在跑。
- 新增常量 `STILL_ACTIVE = 259`。
- 按 `AGENTS.md` 第三条硬约束补 `argtypes/restype`：`OpenProcess` / `CloseHandle` 的
  HANDLE 取 `c_void_p`（否则 32 位截断），`GetExitCodeProcess` 的 `POINTER(c_uint32)`。
- `GetExitCodeProcess` 失败（权限不足等）时**保守判"活着"**，仍交给时间阈值裁决 ——
  不因为问不到就把别人的锁删掉。

### 2.6 验证

| 命令 | 结果 |
| --- | --- |
| `tools/test_gate_lock.py` | **16 PASS / 0 FAIL**（新增第 5 节 4 条） |
| `tools/_qc_gate_lock_mutation.py` | **五刀全红 + 还原字节一致 True** |
| `python -m compileall -q src tools main.py` | exit 0 |

新增的 4 条回归（第 5 节）：

1. 子进程已退出（`poll()` 非 None）；
2. `Popen._handle` 非 None —— **复现条件成立**（句柄还被持有）；
3. 已退出的 PID 判为已死；
4. 拿这个 PID 写锁，`acquire()` 必须能拿到。

变异第五刀 E（`return code.value == STILL_ACTIVE` → `return True`）被抓住的报错正是
`FAIL 僵尸 PID 的锁不阻塞新一轮 ← 已有 check_all 在跑` —— 说明这道判据真的在守这件事。

## 3. 缺陷 B：`test_wake_word.py` 在干净 venv 里必现假红（用例缺件，不是产品缺陷）

### 3.1 现象

只装 `requirements-test.txt` 的 venv 里跑 `tools/check_all.py`，"唤醒词命中"闸门红：

```
NameError: name '_PINYIN_DICT_RAW' is not defined
  at src/voice/wake_word.py ... _homophones()
  at make_det(pinyin=True)  ← src/tests/test_wake_word.py 第 1 节
```

### 3.2 根因（两处独立的缺件）

1. **`pypinyin` 只在运行依赖里。** `test_wake_word.py` 第 1 节验的是"同音字语法扩张"，
   必须读 pypinyin 的真实字典；而 `requirements-test.txt` 没有它，`ci.yml` 的 SKIP 清单
   又把该用例排除了 —— 于是"干净 venv + check_all"这条没人走的路径上必红。
2. **第 10 步的 `importlib.reload(ww)` 会重新执行模块顶部的 `from vosk import
   KaldiRecognizer`**，而本用例从头到尾只装假 vosk（导入后立刻被弹掉）→ 这里报的是
   `ModuleNotFoundError: No module named 'vosk'`，**根本没验到**本意要验的"pypinyin 缺失
   时降级不崩"。

### 3.3 已排除的假设

| 假设 | 结论 | 证据 |
| --- | --- | --- |
| `wake_word.py` 自己引用了未定义名字（产品缺陷） | 排除 | 同文件在装了 pypinyin 的 venv 里能跑通；`_PINYIN_DICT_RAW` 在 `_HAS_PINYIN` 分支里定义 |
| CI 会拦住它 | 排除 | `ci.yml` 的 SKIP 清单包含 `test_wake_word.py`，clean venv 这条路径 CI 不覆盖 |
| 只是"没装包"，加依赖就完事 | 不完整 | 加完 pypinyin 后第 10 步仍报 `ModuleNotFoundError: vosk`（本轮实测），故两处都改 |

### 3.4 改动

- `requirements-test.txt`：末尾加 `pypinyin>=0.50`，附 5 行说明来历（CI 不跑该用例，不影响 CI 耗时）。
- `src/tests/test_wake_word.py`
  - import 之后加**前置断言**：`if not ww._HAS_PINYIN: print("FAIL 本用例需要 pypinyin：pip install pypinyin（requirements-test.txt 已声明）"); sys.exit(1)` —— 缺失时报"因"而不是甩 traceback。
  - 第 10 步：两次 `importlib.reload(ww)` 前后补 `sys.modules["vosk"] = FakeVosk("vosk")`，结束后按 `_orig_vosk` 恢复。

### 3.5 验证

| 场景 | 结果 |
| --- | --- |
| 装 pypinyin 后跑 `src/tests/test_wake_word.py` | **全部通过**（10 节全绿，exit 0） |
| `PYTHONPATH` 指向一个 `raise ImportError` 的 pypinyin 桩（模拟缺包） | 输出 `FAIL 本用例需要 pypinyin：pip install pypinyin（requirements-test.txt 已声明）`，**exit 1**（不再 NameError） |
| `tools/check_requirements.py --strict` | exit 0「✓ 依赖声明完整」（57 个第三方 import：已声明 56 / 注释排除 1 / 未装未声明 0） |

## 5. 诚实边界

- 本机**没有 git**，所以 `test_pack_for_teammate.py` 与两个依赖 git 的打包闸门**没法验**；本 PR 也走了 GitHub API（fork → 分支 → 提交 → PR）。
- doctor 自检结构那 3 项**没有逐项取证**（该用例在 CI SKIP 清单内），归到"需真机/依赖"一类是保守归类，不是结论。
- 变异第五刀只覆盖"判据退化成只看 OpenProcess"这一种退化；`GetExitCodeProcess` 失败时退回保守判活的路径**没有专门变异刀**（它的失败模式是"偶尔多等 45 分钟"，不是"删错锁"）。
- 第 1 节的 24 个脚本自检是"按 SKIP 清单补跑的"，不等于 `ci.yml` 两个 job 的全绿结果；CI 上仍可能有本机看不到的差异。
